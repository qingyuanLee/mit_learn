---

## 一、一句话：分布式系统在解决什么？

**把一台机器干不完的事，拆到多台机器上一起干，同时让用户感觉像是在用一台机器。**

这句话里藏着所有难题：
- "干不完" → **扩展性**问题
- "多台机器" → **网络**问题
- "像一台机器" → **一致性**问题
- 机器会挂 → **容错**问题

## 四、每个问题域在解决什么？

### 问题域 1：共识（Consensus）
**要解决：** 多个节点怎么对一个"值"达成一致？

| 子问题 | 代表方案 |
|---|---|
| 谁来做决策？ | 主选（Leader-based）vs 民主（Quorum-based） |
| 主挂了怎么办？ | 选举（Raft）、租约（Lease）、心跳（GFS） |
| 不一致怎么办？ | 多数派（Quorum）、日志匹配 |
| 节点作恶怎么办？ | PBFT、PoW |

**代表系统：** Raft、etcd、ZooKeeper (Zab)、Viewstamped Replication、PBFT、Bitcoin

---

### 问题域 2：复制（Replication）
**要解决：** 怎么把一份数据放到多台机器上，提高可用性和读性能？

| 复制方式 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **主从（Leader-based）** | Raft、GFS、MySQL主从 | 一致性好、简单 | leader 瓶颈、切换慢 |
| **多主（Multi-leader）** | 全球数据库、CockroachDB | 多活、低延迟 | 冲突解决复杂 |
| **无主（Leaderless）** | Dynamo、Cassandra | 永远可写、抗分区 | 一致性弱、读修复 |

**代表系统：** GFS、Dynamo、Spanner、CockroachDB、Cassandra

---

### 问题域 3：一致性（Consistency）
**要解决：** 复制后，客户端读到的数据到底"有多新"？

```
强一致性 ←————————————————————→ 最终一致

Linearizability    Sequential    Causal    Read-your-writes    Eventual
(线性一致)         (顺序一致)     (因果)     (读己之写)          (最终一致)
    ↑                ↑            ↑            ↑                  ↑
  etcd/Spanner     理论        COPS         Session           DNS/Dynamo
  Raft leader
```

**核心权衡：** 一致性越强 → 延迟越高、可用性越差
CAP 定理：网络分区时，你只能在 **C（强一致）** 和 **A（可用）** 之间二选一。

---

### 问题域 4：容错（Fault Tolerance）
**要解决：** 节点挂了、磁盘坏了、网络断了，系统怎么办？

| 容错手段 | 解决什么 |
|---|---|
| **持久化（Persistence）** | 节点重启后状态不丢 |
| **快照（Snapshot）** | 日志无限增长怎么办 |
| **心跳（Heartbeat）** | 怎么知道节点死了 |
| **超时重传（Retry）** | 消息丢了怎么办 |
| **幂等（Idempotency）** | 消息重复了怎么办 |
| **降级（Degradation）** | 部分挂了还能做什么 |

---

### 问题域 5：扩展性（Scalability）
**要解决：** 数据量太大、QPS 太高，单机扛不住怎么办？

| 扩展方式 | 解决什么 |
|---|---|
| **分片（Sharding）** | 数据切分到多台机器 |
| **分区（Partitioning）** | 按 key 范围 / hash 切分 |
| **负载均衡（LB）** | 读请求分散 |
| **缓存（Caching）** | 挡在数据库前面 |
| **就近访问** | 数据放在离用户近的地方 |

**代表系统：** Spanner、DynamoDB、Bigtable、Lab 5 Sharded KV

---

### 问题域 6：分布式事务（Distributed Transactions）
**要解决：** 一个操作要改多个分片的数据，怎么保证全部成功或全部失败？

| 方案 | 一致性 | 性能 | 代表 |
|---|---|---|---|
| **2PC** | 强一致 | 慢、阻塞 | Spanner |
| **3PC** | 强一致 | 仍慢 | 少见 |
| **OCC** | 强一致（无冲突时） | 快 | FaRM |
| **Saga** | 最终一致 | 快 | 微服务 |
| **TCC** | 最终一致 | 快 | 金融 |

## 五、系统全景：这些技术怎么组合？

```
                一致性级别
                  ↑
   强一致 ────────┼──────── 最终一致
                  │
   ┌──────┐      │
   │Spanner│      │        ┌──────────┐
   │(2PC+  │      │        │ DynamoDB │
   │TrueTime)│     │        │(无主复制)│
   └──────┘      │        └──────────┘
                  │
   ┌──────┐      │        ┌──────────┐
   │etcd/ │      │        │ Cassandra│
   │Raft  │      │        │          │
   └──────┘      │        └──────────┘
                  │
   ┌──────┐      │
   │ZooKeeper│   │        ┌──────────┐
   │(Zab) │      │        │  DNS     │
   └──────┘      │        └──────────┘
                  └────────────────────→
```

**观察：**
- **强一致阵营**：Raft / Zab / Paxos 家族 → 选主 + 多数派复制
- **最终一致阵营**：Dynamo / Cassandra → 无主 + 向量时钟 + 读修复
- **中间地带**：Spanner 用 TrueTime 做到全球强一致；CockroachDB 用 Raft + HLC
