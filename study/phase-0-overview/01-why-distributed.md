# 为什么需要分布式？

> 阶段 0 · 第一篇
> 目标：理解分布式系统的**根本动机**，知道为什么单机不够用了。

---

## 1. 单机的天花板

一台机器的能力是有上限的：

| 维度 | 单机上限 | 突破方式 |
|---|---|---|
| **存储** | 磁盘容量、IOPS | 分布式文件系统（GFS） |
| **计算** | CPU 核数、内存 | 分布式计算（MapReduce） |
| **网络** | 单机带宽 | 分布式缓存（Memcached） |
| **可靠性** | 机器会挂、磁盘会坏 | 数据复制（Raft） |
| **地理位置** | 只能部署在一个机房 | 全球复制（Spanner） |

---

## 2. 分布式系统要解决的三件事

### 2.1 横向扩展（Scale Out）
**问题：** 数据量 / QPS 涨了，加机器就行，不用换更强的单机。

**例子：**
- 淘宝双 11：单台数据库扛不住，拆成几百个分片
- 微信消息：几百亿条消息，分散在几千台服务器

### 2.2 高可用（High Availability）
**问题：** 单台机器挂了，服务不能停。

**例子：**
- 支付系统：一台数据库挂了，另一台立刻接管
- DNS：全球多个副本，一个挂了还有别的

### 2.3 地理分布（Geo-distribution）
**问题：** 用户遍布全球，数据要放在离用户近的地方，降低延迟。

**例子：**
- 视频网站：CDN 把视频缓存到全球边缘节点
- Spanner：全球数据库，每个大洲都有副本

---

## 3. 单机 vs 分布式：复杂度对比

| 维度 | 单机 | 分布式 |
|---|---|---|
| **故障** | 整个机器挂 | 部分机器挂，部分正常 |
| **网络** | 内存调用 | 网络调用，可能丢包/延迟 |
| **时钟** | 一个时钟 | 多台机器，时钟不同步 |
| **并发** | 单线程/多线程 | 多节点同时操作 |
| **一致性** | 天然一致 | 怎么保证一致是核心难题 |

> **关键洞察：** 分布式系统的复杂度，几乎全部来自"多台机器"带来的不确定性。

---

## 4. 分布式系统的"不可能三角"

```
          一致性 (Consistency)
              /\
             /  \
            /    \
           /      \
          /        \
         /          \
        /            \
       /______________\
可用性 (Availability)  分区容错 (Partition Tolerance)
```

**CAP 定理：** 网络分区（P）一定会发生；此时你只能在 C 和 A 之间二选一。

- **选 C（强一致）：** 分区时少数派不可写（Raft、etcd、ZooKeeper）
- **选 A（可用）：** 分区时仍可写，但可能不一致（Dynamo、Cassandra、DNS）

---

## 5. 常见误解澄清

| 误解 | 真相 |
|---|---|
| "分布式就是更快" | 不一定。分布式有网络开销，小规模可能比单机慢 |
| "分布式就是更可靠" | 不一定。分布式组件更多，故障点也更多 |
| "分布式就是把代码跑在多台机器上" | 不是。核心难点是处理**不确定性** |
| "CAP 说三者只能选二" | 更准确地说：P 是必选的，你只能在 C 和 A 之间选 |
