## 1. 一句话问题

**Facebook 有几十亿用户，每次读都查 MySQL 数据库会爆炸。怎么用一层分布式内存缓存挡在数据库前面，并且在缓存节点宕机时不让整个网站雪崩？**

---

## 2. 架构

```
Client (Web Server)
    │
    ▼
┌──────────────────────────┐
│  Memcached 集群 (数百台) │  ← 纯 KV 缓存，无主、无复制
│  每个 key 哈希到某台     │
└──────────┬───────────────┘
           │ cache miss
           ▼
      MySQL / 数据库
```

---

## 3. 关键设计：缓存一致性策略

- **不写穿（write-through）**：数据库更新后**主动失效**缓存（delete key，不是 update）。
- **为什么 delete 而不是 update？** 因为可能有多个并发写，update 会覆盖错；delete 最简单。
- **Cache miss 时回源数据库**：数据库返回后顺便回填缓存。

---

## 4. 雪崩与击穿

| 问题 | 现象 | Facebook 的对策 |
|---|---|---|
| **雪崩（avalanche）** | 大量缓存同时过期 → 数据库被打爆 | 过期时间加随机抖动 |
| **击穿（hot key miss）** | 一个超热 key 过期 → 大量请求同时打到数据库 | 单飞机制（single-flight）：只让一个请求去查库，其他等结果 |
| **缓存节点宕机** | 这台节点上的所有 key 都 miss → 数据库被打爆 | **不做复制**，但用**分层缓存**（本地 LRU + 远程 Memcached） |

---

## 5. 为什么不做复制？

- Memcached 是缓存，不是持久存储。
- 复制会让写放大（每台都要更新）。
- 节点挂了就让那批 key 自然过期，数据库扛得住（因为有本地缓存 + 限流）。

---

## 6. FAQ

**Q: 为什么缓存层用哈希分片而不是一致性哈希？**
A: 早期用一致哈希，但节点增减时全量迁移，压力大；后来改用**代理层**（mcrouter）做路由。

**Q: mcrouter 是什么？**
A: Facebook 的缓存代理，负责把 key 路由到正确的 Memcached 节点，还支持复制、池化、故障转移。
