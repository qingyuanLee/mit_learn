## 1. 一句话问题

**亚马逊需要一个"永远可用、永远能写、永远不宕机"的 KV 存储，哪怕网络分区、哪怕数据中心挂了。怎么在强一致和高可用之间选后者？**

Dynamo 的答案：**最终一致 +  sloppy quorum + 读修复 + hinted handoff**。

---

## 2. 核心技术组合

| 技术 | 作用 |
|---|---|
| **一致性哈希（带虚拟节点）** | 数据按 key 哈希分到 N 个节点，节点增减时只迁移少量数据 |
| **Sloppy Quorum** | 读写不要求"原始 N 个节点"，只要 N 个健康节点响应即可；不在原始节点上的数据叫 "hinted" |
| **Hinted Handoff** | 如果原本该存到节点 A 的数据，A 挂了，先存到节点 B；A 恢复后 B 把数据交还 |
| **读修复（Read Repair）** | 读多个副本时如果发现副本不一致，在读返回时顺便把旧副本修好 |
| **向量时钟（Vector Clock）** | 标识版本，如果出现"分叉"（两个写没有因果关系），让应用来合并 |

---

## 3. 与 Raft 的哲学对比

| | Raft | Dynamo |
|---|---|---|
| 一致性 | 线性一致 | 最终一致 |
| 分区时 | 少数派不可写 | **仍然可写** |
| 冲突 | 不允许 | 允许，应用合并 |
| 典型场景 | 内部 KV、配置存储 | 购物车、会话、用户偏好 |

> **CAP 选择**：Raft 选 C，Dynamo 选 A。Amazon 的购物车在网络分区时仍然要能加东西——可用性比"绝对一致"更重要。

## 4. 2023 版的演进

- 早期 Dynamo 是最终一致；**DynamoDB（云产品）**提供了**强一致读**选项。
- 底层用 SSD + 全局二级索引 + 自动扩容。
- 全球表（Global Tables）跨区域多活，用最后写入胜出（LWW）。

## 5. FAQ

**Q: 向量时钟怎么用？**
A: 每次写带一个 `[(node1, counter), (node2, counter)]`；两个版本如果有因果关系，时钟是包含的；否则就是冲突，应用合并。

**Q: 为什么购物车要最终一致？**
A: 网络分区时，用户在手机上和电脑上同时加东西，比"一个端不能用"体验更好。

**Q: 银行账户余额能用 Dynamo 存吗？**
A: 不能。金额不能"最终一致"，必须用 Raft/Spanner 这种强一致系统。
