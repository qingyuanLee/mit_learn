# 一致性模型（Consistency Model）速查

> 对应 LEC 4。分布式系统的"正确性"问题本质上是在问：**一个操作何时能被其他节点/客户端观察到？**

---

## 1. 一张表看全部

| 模型 | 顺序保证 | 性能 | 典型系统 |
|---|---|---|---|
| **Linearizability（线性一致性 / 强一致）** | 所有操作有一个全局时序，且与"真实时间"一致；未完成的操作看起来像从未发生 | 最差（需要多数派 / 同步） | ZooKeeper、etcd、Raft、Spanner |
| **Sequential Consistency（顺序一致性）** | 所有操作有一个全局顺序，但**不要求与真实时间对齐** | 次差 | 早期多处理器内存模型 |
| **Causal Consistency（因果一致性）** | 只保证有因果关系的操作按序；并发操作可乱序 | 中 | COPS、MongoDB（部分场景） |
| **Read-your-Writes / Session** | 同一个客户端自己写的自己能立刻读到 | 较好 | 多数 KV 存储（客户端层实现） |
| **Eventual（最终一致）** | 不保证中间态，最终收敛 | 最好 | DNS、Dynamo、Cassandra |

---

## 2. Linearizability 的精确定义

给定每个客户端的调用 / 返回事件（线性化历史），能否找到一个**全局点序** S，使得：

1. **实时性约束**：若操作 A 的返回早于操作 B 的调用，则 S 中 A 在 B 之前。
2. **每个操作都在其调用→返回区间内选定一个"生效点"**。
3. 顺序 S 执行的结果与单个寄存器（状态机）的串行语义一致。

### 关键推论

- 读操作也必须"生效"——也就是说，读到旧值是不允许的，哪怕读发生在两个写之间的网络延迟窗口里。
- **未完成的操作**（调用了但没返回）可以出现在历史里，也可以不出现——这正是 Lab 2 里 client 要"重试还是丢弃"的根源。
- 线性一致性是**全局**的，不按 key、不按用户分桶。

---

## 3. 为什么它贵？

| 代价 | 来源 |
|---|---|
| 同步延迟 | 写必须等到多数派持久化才能 ack |
| 可用性损失 | 多数派节点挂了 / 分区了，服务不可写 |
| 读延迟 | 强一致读要么读 leader，要么读 quorum + 校验 |

**CAP 的真相**：网络分区（P）一定会发生；此时要在 C（强一致）和 A（可用）之间二选一。Raft/ZooKeeper 选 C，Dynamo/Cassandra 选 A。

## 4. 自测：下面这个历史是否 linearizable？

```
Client X:  W(x)=1 -------->
Client Y:              R(x) ---------> 读到 1
Client Z:                          W(x)=2 -------->
Client Y:                                      R(x) --> 读到 2
```

✅ 是：W(x)=1 生效点在 R(x)=1 之前，W(x)=2 在其后。

```
Client X:  W(x)=1 -------->
Client Y:          R(x) ---------> 读到 2   ←？
Client Z:                      W(x)=2 -------->
```

❌ 否：Y 的读开始时 X 的写已返回，按实时性 Y 必须看到 1；读到 2 不合法。
